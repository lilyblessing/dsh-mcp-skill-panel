## 二、安全面改动详解

### 2.1 MCP 行校验
```ts
const entry = ctx.loader.resolve(entryId)
if (!isMcpEntry(entry)) throw new Error(`entry "${entryId}" is not an MCP row`)
```
- `isMcpEntry`（`src/mcp-entry.ts`）：`options.name === '@deepseek-ai/dsh-mcp-client'` 或 config 含 `serverName` 且非 group 行的判定。
- 修复前：调用方传入任意 loader 行 id 即可 `entry.update({disabled})`——攻击面含核心行/其他插件行。

### 2.2 写操作 token 鉴权
- `PANEL_TOKEN = randomBytes(32).toString('hex')`（`node:crypto`，模块级，随插件实例生成）。
- `handle(method, run, guarded)` / `handleAny(entries, guardPosts)`：POST 且 `req.headers['x-panel-token'] !== PANEL_TOKEN` → 401。
- client 侧 `ensureToken()`：`fetch('/api/mcp-skill-panel/token')` 缓存 Promise，POST 前自动带 `x-panel-token` 头。
- **威胁模型**：阻断「跨源页面 / DNS-rebinding 对本地控制端点盲写」。跨源页面因 SOP 读不到 `/token` 响应。GET 只读端点（`state`/`config`/`debug`/`token`）保持开放，面板数据非敏感。
- **已知边界**：不防「本机进程」（token 在进程内，任意本机用户态进程仍可调用）；宿主 webServer 无鉴权层，绑 `0.0.0.0` 时需外层网络隔离。

### 2.3 readBody 上限
- `MAX_BODY_BYTES = 64 * 1024`；超限 `req.destroy()` + reject（handle 落 400）。
- 顺带补 `req.on('error')`，并移除已传输事件监听（`cleanup`），避免断流后误 resolve。

### 2.4 waitRegistered 生命周期绑定
- 新增 `ctx.effect(() => () => finish(new Error('context disposed')), 'mcp-skill-panel: waitRegistered')`：上下文销毁立即终局。
- 新增 `signal` 参数（透传 `exec.signal`）：已中止 / `abort` 事件 → 立即 reject。
- 任何路径（注册成功 / 超时 / 销毁 / 中止）都保证 settle，不再挂起 `mcp_call`。

## 三、构建与发布踩坑实录

> 以下踩坑在**本仓库**实测（Windows + DSH 环境），对「在 DSH harness 进程中构建/发布插件」的场景通用。

### 3.1 构建顺序坑（本次实锤，最重要）
- **现象**：`npm run build` 后 `lib/types` 永远不存在 → package.json `types`/`exports["./types"]` 悬空。
- **根因**：`build.mjs` 原顺序是「tsc dts → tsdown」；tsdown 配置 `clean: true`（node 入口清 `lib/`），把 tsc 刚生成的 `lib/types` 一并删掉。
- **修复**：调换为「**tsdown → tsc dts**」，并在 `verify.mjs` 加 `lib/types/*.d.ts` 存在性断言防回归。

### 3.2 空 package-lock 坑
- **现象**：仓库 `package-lock.json` 是 **0 字节空文件**（`git show HEAD:package-lock.json` 为空）——npm 无法据此复现依赖。
- **影响**：新装者 `npm install` 会重新解析、锁文件漂移。
- **修复**：重建 lockfileVersion=3 合法锁（本次用 `npm install --legacy-peer-deps` 生成后校验 `JSON.parse` 通过）。

### 3.3 DSH harness 内 npm 环境继承坑
- **现象**：`npm install` 报「up to date in 300ms」但 `node_modules` 为空、且把仓库 lockfile 清空。
- **根因**：DSH harness 自身是 `npm exec dsh` 拉起的，pwsh 会话继承 `npm_config_local_prefix`（→ workspace 根）与 `npm_package_json`（→ workspace 根的 package.json）——npm 把「项目根」解析到了 harness 目录，而非插件目录。
- **规避**：命令内先覆盖环境变量再装：
  ```powershell
  $env:npm_config_local_prefix = '<repo>'
  $env:npm_package_json = "<repo>\package.json"
  npm install --prefix <repo> --legacy-peer-deps --no-audit --no-fund --cache <备用cache>
  ```
- 注意：本仓库「锁文件被 npm 清空」时，先 `git checkout -- package-lock.json` 恢复（但 HEAD 本就是空锁，见 3.2）。

### 3.4 沙箱 spawn EPERM 坑
- **现象**：workspace-write 沙箱内 `npm install` 在生命周期/rebuild 步骤报 `spawn EPERM`（errno -4048）。
- **根因**：沙箱限制子进程以管道方式抓取输出（命名管道被禁）。
- **规避**：纯 JS 工具链加 `--ignore-scripts`（esbuild 走 optionalDependencies 二进制，无需 postinstall）；仍需 spawn 时，到 **danger-full-access 沙箱外**执行一次。

### 3.5 闭包类型 junction 坑
- 构建期依赖 DSH 闭包类型：`npm run setup`（`scripts/setup-dsh-deps.mjs`）把所有 `~/.dsh/profiles/node_modules/@deepseek-ai/*` junction 进本仓库 `node_modules/@deepseek-ai`（185 个）。
- `tsconfig.json` 的 `paths` 指向这些 d.ts；必须在 `node_modules` 存在后再跑 setup。
- junction 不提交（`node_modules/` 被 .gitignore），别人 clone 后需自己 setup。

### 3.6 ctx.timeout 语义确认（非坑，消除误判）
- `await ctx.timeout(delay)`（无回调）在 DSH 的 `cordis-plugin-timer` 里返回**延时后 resolve 的 Promise**（非轮询忙等）——`toggleSkill` 的 5s 确认循环是真休眠，无忙等问题。

## 五、部署与取舍

- **生效方式**：git 源一行安装契约不变（`lib/` 已入库，无需构建）；安装/更新后**重启 `dsh web`**（bundle 层启动时合成）。
- **升级命令**：
  ```sh
  dsh plugin --profile web add "github:lilyblessing/dsh-mcp-skill-panel#main"
  ```
- **取舍**：
  - 写操作 token 防「网络侧/跨源盲写」，不防「本机进程」——如需更强需宿主层鉴权。
  - 旧前缀 `/api/runtime-inventory/*` 保留兼容（服务端双注册），但 client 已统一新前缀。
  - `mcp_search`/`mcp_call` 报错文案仍为中文硬编码，与双语 UI 不一致（小额待办，尚未处理）。
