## 二、 关键维度专题调研与深度剖析

### 1. 变更日志（Changelog）的处理范式
- **业界共识**：**严禁在 README 正文堆砌历史版本变更细节**。
- **高星项目的做法**：
  1. `tt-a1i/archify`：在顶部徽标区展示版本号徽标，点击该徽标直接跳转至 `CHANGELOG.md` 中对应版本的锚点（例如 `CHANGELOG.md#320--2026-10-18`）。
  2. `deepseek-ai/deepseek-harness` 与 `morluto/rea`：README 完全不放置变更日志，完全依靠 GitHub Releases 或独立的版本发布记录。
  3. `modelcontextprotocol/typescript-sdk`：仅在重大破坏性版本迭代时，在首屏使用 `> [!IMPORTANT]` 提示当前分支主版本状态及迁移指南链接（`migration/upgrade-to-v2`）。
- **反观当前仓库**：
  - `dsh-mcp-skill-panel` 现有 README 中，「📋 变更日志」占据了第 297 至 447 行（**151 行，占总行数 33.5%，占总文本大小近 40%**），巨细靡遗地记录了从 v0.6.0 到 v0.1.0 内部每次 bug 修复、PR 编号、提交散列值甚至开发期未发布的草稿版本。
  - **弊端**：普通用户在阅读时被迫划过长达数屏的技术历史流水账，完全淹没了安装与配置等核心信息；且移动端与 npm 页面加载极重。

### 2. 深度设计与原理解析（Deep Design）的处理范式
- **业界共识**：**README 负责「价值呈现与快速上手」，`docs/` 负责「原理深究与运维架构」**。
- **高星项目的做法**：
  1. `morluto/rea`：仅在 README 留 4 行文字阐述 MCP 交互机制，配一张高清晰度的架构工作流图（`rea-investigation-flow.svg`），具体底层协议与调用契约全部沉淀为 [docs/mcp-contracts.md](file:///D:/software/HarnessWorkspace/dsh-plugin-develop/dsh-mcp-skill-panel/docs/mcp-contracts.md)。
  2. `astral-sh/uv`：在 Features 章节中仅展示基础命令行输入输出效果，详细的工作区设计、缓存原理统一外链至专门的概念文档（`docs.astral.sh/uv/concepts/...`）。
  3. `deepseek-ai/deepseek-harness`：README 只有 65 行，架构哲学仅引用论文链接与 Cordis 说明，具体 Web UI 运行逻辑与配置全部分流入 `docs/user/guide/`。
- **反观当前仓库**：
  - 包含了大量内部历史包袱，如「运行期绝不写预设文件是 0.1.x 行为，0.2.0 已废弃……因 WeakMap 导致崩溃」这类事故复盘和底层数据结构分析。这些内容属于**开发维护与架构留档**，误塞入面向最终用户的 README 中，大幅增加了使用者的认知负荷。

### 3. 首屏演示与视觉引导（Demo / Visuals）
- **业界共识**：**首屏 30~50 行内必须完成「定位、视觉冲击、一句安装」三件套**。
- **高星项目的做法**：
  1. `morluto/rea`：第 9-35 行完成多语言、一句话 Slogan、徽章、快捷安装命令 `npx rea-agents setup`，第 47 行直接给出大幅动态分析截图。
  2. `tt-a1i/archify`：第 17 行放置 Hero 截图，第 61 行放置 35 秒视频/动画演示，第 72 行立即给出安装命令。
  3. `astral-sh/uv`：第 21 行放置 Benchmark 柱状图，紧接着是核心亮点与安装脚本。
- **反观当前仓库**：
  - 首屏虽有截图 `docs/images/mcp-panel.jpg`，但安装命令竟被推到了第 132 行！用户必须先看「核心能力大表格、配置项大表格、两种形态 Mermaid 状态图/流程图、生效时机 Prompt Cache 计费倍率详解」才能看到如何安装。

### 4. 多语言维护（Multilingual Strategy）
- **业界共识**：**`README.md` 默认使用英文已是 GitHub 全球开源生态的绝对惯例，中文采用 `README.zh-CN.md`（或 `README.zh.md`）**。
- **高星项目的做法**：
  1. `deepseek-ai/deepseek-harness`：根目录 `README.md` 为英文，中文对应 `README.zh.md`，顶部第一行提供互相跳转链接。
  2. `esengine/DeepSeek-Reasonix`：根目录 `README.md` 为英文，中文对应 `README.zh-CN.md`。
  3. `morluto/rea`：根目录 `README.md` 为英文，其他 20 种语言统一收纳于 `docs/readme/README_<lang>.md`。
- **反观当前仓库**：
  - 当前根目录 `README.md` 是中文，`README.en.md` 是英文。这在 npm 包展示和海外开发者浏览时，首先呈现的是中文，与国际开源主流习惯颠倒。

## 四、 高星项目 README 共性范式总结（5 大黄金准则）

1. **首屏 30 行触达准则（30-Line Rule）**：
   - 顶部 30 行内必须包含：项目名称、一句话业务定位、核心效果展示（图片/GIF）、以及一行可直接复制的安装或体验命令。
2. **安装前置与开箱即用准则（Install-First Principle）**：
   - 安装指南紧随首屏之后，提供明确的运行前提（如 DSH 兼容版本）与开箱即用命令，决不让架构长篇大论阻隔用户上手。
3. **日志彻底脱耦准则（Clean Changelog Principle）**：
   - README 正文只保留当前版本徽标，历史变更全量独立存储在根目录 `CHANGELOG.md` 中，版本号通过 markdown 锚点精准互联。
4. **渐进式信息暴露准则（Progressive Disclosure）**：
   - README 是「索引看板」，而非「百科全书」。架构图仅呈现宏观意图，实现细节、数据流向、协议细节下沉至 `docs/`。
5. **双语对齐与标准命名准则（Standard Localization）**：
   - 面向通用开发生态时，默认 `README.md` 采用国际通用英文，本地化主语言采用 `README.zh-CN.md`，并在头部醒目互链。
